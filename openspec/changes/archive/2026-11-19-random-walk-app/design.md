# Design

## Context

全新 Android 应用，无既有代码。动机与范围见 `proposal.md`；行为契约见 `specs/walk-guidance/spec.md` 与 `specs/street-data/spec.md`。

塑造本设计的三条硬约束：

1. **单机买断、只发 APK、无后端** —— 排除了任何按调用计费的第三方服务（密钥无法藏进售出的安装包），也排除了运行时代理、聚合缓存、按用户限流。
2. **界面只有一个箭头和一个数字** —— 排除了地图渲染、图例、引导文案、错误对话框这类「有地方放信息」的设计。
3. **路线必须落在真实可走的路网上** —— 排除纯罗盘方案（会指向河对岸、封闭小区、不可达点，且极简 UI 没有任何元素能解释「为什么走不到」）。

## Goals / Non-Goals

**Goals**

- 一个 APK，装上、打开、输入距离就能走；无网的大城市与有网的任意 OSM 覆盖区都能走。
- 罗盘方向在户外可用：不需要标定，不需要把手机端平，平端/斜端/竖持/换手都收敛到同一个朝向。
- 路线在真实路网上生成，且与用户输入的距离总量吻合。
- 数据分层（预置包 / 瓦片缓存 / 在线兜底）对用户不可见，只体现为「等一下」或「不行」。

**Non-Goals**

- 不做地图可视化（因此完全不需要 GCJ-02，也不用为境内测绘资质场景做设计）。
- 不做震动或声音提示、不做锁屏后继续指引：用户已明确全程把手机端在手里、屏幕是主场，所以一整套「不看屏幕时的降级通道」整体出局。
- 不做省电优化到极致：漫步时会话常开屏幕，接受约 10–15%/小时的耗电。
- 不做路线的「风景质量」评估（路面材质、绿化率等）。
- 不做 iOS、不做平板布局、不做深色主题切换（深色是唯一主题）。

## Decisions

### D1 原生 Android + 单个 Activity + 一块 Canvas

Kotlin + Compose 只用于开始页，漫步页用 `Canvas` 自绘。理由：漫步页的内容是「一根会转的箭头 + 一行数字」，任何 UI 框架的布局与重组都在为不存在的东西付代价；Canvas 每帧重绘的成本可预测，且天然只能画这两样东西——架构上就无法偷偷加控件。

**替代方案**：Flutter/RN（多一份运行时与包体积，且未来 iOS 复用收益在「只发 APK」的前提下不存在）；Jetpack Compose 动画（旋转要 60fps 跟随传感器，重组模型不如直接重绘直观）。

### D2 箭头采用「世界固定」，用旋转矢量而非裸磁力计

屏幕角度 = `目标方位 − 设备朝向`。因此箭头朝上 ⇔ 设备正对目标，用户靠**转身**对齐，而不是转手机。

- 朝向来自 `TYPE_ROTATION_VECTOR`（加速度计 + 磁力计 + 陀螺的九轴融合），不是裸 `TYPE_ORIENTATION`：后者在磁干扰下会抖到不可用。
- 手机在漫步中会被平端、斜端、竖持，甚至换手，所以「设备的正前方」不是一个固定轴。不要在两个轴之间做交接，而是解析地合成：设俯仰角为 θ（θ=0 平放、θ=90° 竖持），则

  ```
  Ŷ  =  cosθ·前 + sinθ·上
  −Ẑ =  sinθ·前 − cosθ·上
  cosθ·Ŷ + sinθ·(−Ẑ) = 前        // 恒等，与 θ 无关
  ```

  因此：`前向(设备系) = cosθ·Ŷ − sinθ·Ẑ`，`世界前向 = R · 前向(设备系)`，`方位 = atan2(世界前向.东, 世界前向.北)`。θ 从同一个旋转矩阵取，不需要额外传感器。

  这个式子使平放 / 竖持 / 斜端 / 换手 / 垂手在身侧全部收敛到同一个结果；绕前向轴的身体侧倾（roll）不影响计算结果；45° 那个最危险的姿势反而权重各半、误差最小。
- 平滑：对角度做最短弧低通，时间常数 0.2 s；**站定不冻结**（冻结会让用户在路口原地转身时箭头不动，等于毁掉对齐操作）。
- 磁力计精度低时把时间常数拉到 1–2 s：退化成「变慢」，而不是「变疯」。

**替代方案**：屏幕固定的北向上指针（不需要磁力计，但无法告诉用户往哪转身——已否决）；按俯仰角在 `+Y` / `−Z` 两轴之间交接（`pitch < 30°` 用 `+Y`、`> 60°` 用 `−Z`、中间过渡）——**已否决**：交接带恰好落在 45° 这个最常见的斜端姿势上，两轴权重互相打架，手抖或转弯时朝向会跳，而「箭头稳」是本产品唯一的技术承诺。矢量求和没有交接带，同精度下不需要任何标定或「把手机端平」的引导。

### D3 箭头指向「路径前方 25 m」的点，不是终点

用户离下一个路口很近时，指向终点的方位角会剧烈摆动（方位角在近距离处是奇点）。改为沿当前路径前进 25 m 取一点算方位，箭头因此在整段上几乎恒定，只在过路口后跳变一次——这恰好是用户需要的语义（"这段往那边走"），也比指向终点更符合"顺势走"的体验。

### D4 路线在图上随机游走，只在路口决策

- 状态机只有三个：`待决策 → 已定向（沿当前边前进） → 到达（回到待决策）`。
- 段长在候选路口集合上筛选：优先 180–400 m；10% 概率放宽到 600–900 m。
- 转角 `< 20°` 的承接不算决策（真实道路上一条路会微微弯曲，若每次弯曲都重新决策，段会碎成 50 m 的小片段）。
- 排除 `|转角| > 150°` 的候选（即掉头）。
- 左右各 50%；约 20% 的概率"到下一个路口再说"（在候选里挑一个直行方向，把决策推迟）。

**替代方案**：在起点随机取一个远端终点再求最短路。否决理由——最短路会贴主干道走，路线单调且可预测；而"每 200–400 m 重新掷骰子"才产生漫步需要的无序感，也天然保证掉头概率低。

### D5 预算动态分配，回程用「预算耗尽」触发

不预先切分「去程 X 米、回程 Y 米」。每一步按 `剩余预算 / 预计剩余段数` 决定本段目标长；回程的触发条件是 `剩余预算 ≤ 回家直线距离 + 100 m`——于是用户永远在预算用尽的那一刻刚好走到家门口附近，而不是先走完去程再独自面对一段没预算的回程。

回程路线由同样的随机游走产生，但排除去程已用过的边（有替代时）。回家距离用一次带半径上限的 Dijkstra 得到，半径取剩余预算，无解则视为「离家太远」，直接以当前点为终点结束。

### D6 到达判定用「沿边投影」，并用时间滞后吸收噪声

判定条件：距当前边终点节点 `< 10 m`，或 `沿当前边的投影进度 ≥ 95%`；条件需持续 1.5 s 才生效。

前者处理"走到路口停下"，后者处理"直接走过路口没停"——GPS 5 s 一次采样，用户可能已经在新边上。时间滞后是为了让阈值附近的 GPS 抖动不产生"连续两次到达"。

### D7 数据源只能是 OSM，这是商业模式决定的，不是技术偏好

单一来源：OSM + ODbL。理由不是"免费"，而是**买断制 + 无后端**下唯一可能：任何按量计费的 API 都要求把密钥放进售出的 APK，密钥必然被提取，于是成本是"用户数 × 调用数"，收入是"用户数 × 单价"。

**替代方案**：高德/百度/Google/Mapbox。除计费问题外还有三条独立否决理由：步行路网图不对外开放（只给点到点路线，没有"这个路口有哪些可走邻居"）；高德导航 SDK 会接管界面（自带地图/语音），与"只有一个箭头"直接冲突；GCJ-02 偏移会让 WGS-84 定位与数据错位一个街区。离线切片（如自家 Geofabrik 抽取分发）需要服务器，也出局。

### D8 数据分三层：预置包 → 瓦片缓存 → 在线兜底

- **预置包**：随 APK 内置（体积允许时）或作为静态文件下载的城市级 SQLite。地级市 3–10 MB、特大城市 20–50 MB（节点间距约 30 m 简化后）。对用户完全等价于"装了就能用"。
- **瓦片缓存**：约 2 km 见方的自定义米制网格（不用经纬度瓦片，避免高纬度变形），每块独立写入 SQLite，命中即零网络。瓦片按需扩展：走向边缘前预先取相邻块。
- **在线兜底**：设备直连公开 OSM 数据接口，多镜像轮换 + 有限重试 + 总时限（目标 20 s）。

三层对 UI 的映射只有两种状态：`就绪`（立即开始）与`准备中`（一个进度指示 + 取消）。

### D9 数据模型：节点表 + 有向边表

```
nodes(id, lat, lon)                       -- WGS-84，int32 的 1e-7 度
edges(from_id, to_id, length_m, geometry, way_id)
tiles(tile_id, bbox, fetched_at)          -- 已落地的瓦片，用于跳过重复抓取
```

只存行走相关的 way（`highway` 为 footway/path/pedestrian/living_street/residential/service/unclassified/tertiary 等，且 `access` 不为 `private`/`no`，且不是 `motorway`/`trunk`/`railway`）。边长用 haversine；`geometry` 保留原始折线，供投影计算与绘制（虽然不画地图，但投影需要）。

### D10 就绪判定放在开始页，与输入距离并行

准备在用户输入距离时就并行启动（用户输入 5–10 s，准备 5–20 s，主观等待接近零）。只有当两者都完成才允许开始；准备失败则在开始页给出「该区域无可用步行数据」+ 重试。

**为什么不静默失败**：一款卖给陌生人的单机软件，任何"按了没反应"都会被当作坏掉了，且没有客服渠道。

### D11 首启只做一次性、可跳过的提示

极简界面是优势也是风险：懂的人零学习成本，陌生人打开只有箭头会不知道要转身。折中：**首次漫步时**在漫步页覆盖一层 3 秒提示（"箭头朝上 = 你正对要去的方向，转身对齐它"），只出现一次，长按可立即消失。不做多页引导、不做常驻文案。

### D12 无遥测、无网络权限之外的任何上报

除数据准备外不发任何请求；不做崩溃上报（需要后端）。付费用户的隐私预期与"位置数据"的敏感性决定了这一点，同时它也是"单机 3A"这个定位的一部分。

### D13 城市包的生产是离线脚本，不在应用里

一个 Python 脚本从 OSM 抽取（Geofabrik）或按区域查询，过滤 way、简化节点（约 30 m 间距）、写出 SQLite 包。产物作为静态文件发布（或内置进 APK 的 assets）。运行时应用不认识"城市"，只认"这块区域的瓦片是否已存在"——因此包与在线数据在同一套表结构里，天然可以混用。

## Risks / Trade-offs

- **公开 OSM 数据接口的可用性与政策**（中国大陆不稳定，且政策面向非生产用途）→ 主路径是预置包，在线只是兜底；镜像轮换 + 总时限 + 明确的失败反馈；若销量增长到需要常态在线，必须改为自建实例或改为纯离线包，这是发布后需要盯的成本点。
- **OSM 覆盖不均**（欧洲/北美近乎完整，部分区域稀疏）→ 产品说明必须写"OSM 有数据的地方"，不能写"任意地点"；覆盖判定在开始页就给出结论，而不是让用户走到半路才发现。
- **路线把用户带进死胡同 / 不连通区域**（数据里存在孤岛、或住宅区围墙）→ 生成阶段只使用与当前点同一连通分量的边；走到断头路时按"新的决策"回溯，不显示掉头箭头。
- **磁干扰导致箭头不准**（桥下、高层之间、车内）→ 降低响应速度而非冻结；用户可用"箭头不动就是在变"，比"乱跳"更容易理解。
- **25 m 前瞻与短段的冲突**（段短于 25 m 时前瞻点落到下一段）→ 前瞻距离取 `min(25 m, 段剩余长度)`，并在到达前就切到新段的方位（本设计中已有"接近路口时提前换向"的行为）。
- **极简 UI 对陌生买家的解释成本** → D11 的一次性提示；同时把"箭头 + 距离"本身当作卖点（产品说明靠截图讲清楚）。
- **一次性收入 vs 持续维护**（OSM 数据会变、Android 版本会变）→ 明确定位为"单机游戏式"产品：主要升级靠版本迭代（可作为付费 DLC/新版本），不做服务承诺。
- **ODbL 后果**：分发的数据库包必须允许再分发，法律上买家可用你的包去卖自己的产品 → 现实风险极低，接受；署名与许可声明放「关于」页（长按标题进入）。

## Migration Plan

全新应用，无迁移。发布路径：`debug` 安装包自测 → 内测分发（直接 APK）→ 正式售卖（同一下载物，无账号体系）。回滚策略不适用；数据包版本通过 `tiles.schema_version` 保留字段，未来可整包重建。

## Open Questions

- 预置包的更新节奏（季度 / 半年重生成一次）——不影响实现，先做出"包可替换"的结构即可。
- 长段（600–900 m）的比例是否需要按区域路网密度自适应（稀疏郊区可能取不到 600 m 的段）——先按固定 10%，实测后再调。
